Lycorine iOS 27 Cryptex1 TSS client: on a physical device, import a directory containing Restore/BuildManifest.plist. The app verifies SHA-384 of the four mandatory Cryptex assets and that the trust cache is marked for personalization, reads AppleImage4 chip identifiers and the current cryptex nonce via iDevice, constructs a fresh Cryptex1 request matching public idevice/src/tss.rs, and sends it via HTTPS to gs.apple.com. A new signed local copy is only saved when Apple's response actually contains an Image4 ticket. No installation happens automatically. The original TSS server bug was patched, and a ticket received is not evidence that iOS accepted or installed the cryptex. Test on real hardware; Simulator cannot emulate this. Diagnostics intentionally omit nonces, ECIDs and ticket bytes. Source reference: https://github.com/jkcoxson/idevice/blob/master/idevice/src/tss.rs


## Diagnosing RemotePairing resets

The TCP probe verifies only socket reachability. The optional **Test RemotePairing protocol (no credentials)** button sends one public, unauthenticated `attemptPairVerify` hello in the framed `RPPairing` protocol used by the pinned public iDevice client, and checks the response's structure without printing its contents. It does not read or modify pairing keys, pair the device, or contact Apple TSS.

An RSD reset is **not** sufficient evidence that the pairing file is invalid. A reset **before** an initial protocol reply suggests endpoint/forwarding/protocol problems. A valid hello followed by an RSD failure narrows the problem toward pair-verify, pair-setup, or tunnel negotiation. Use the output to decide which implementation layer to investigate. Source: [iDevice RPPairing socket](https://github.com/jkcoxson/idevice/blob/v0.1.68/idevice/src/remote_pairing/socket.rs).
